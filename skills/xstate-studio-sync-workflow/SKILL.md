# XState Studio ↔ Implementation Sync Workflow

## Core Principle

**Structure is edited only in Studio; exported files are never hand-edited.** A `.ts` file exported from Studio is a read-only snapshot — anything you hand-edit gets silently overwritten by the next Studio export. The implementation layer connects to the export **through names only**.

**Breaking the single-direction flow = your changes WILL be lost, no exceptions.** When structure must change (states / events / transitions / guard names / action names), the correct move is to have the user edit the diagram in Studio and re-export — not for you to edit the exported file.

## Three Layers of Responsibility (Naming Is the Interface)

| Layer | Responsibility | Edited by |
|---|---|---|
| Studio diagram | State structure, transitions, guard/action **names**, simple guards derived from context | The user (graphical editor) |
| Studio export (e.g. `tmp-xstate.ts`) | Read-only snapshot, used for structure review | Nobody (generated by export) |
| Implementation layer (e.g. `interactionSystem.machine.ts`) | All business logic: actions with store/scene side effects, guards reading external state, drag context, etc. | The code repo |

The two sides connect via **names of guards / actions / events / states**: the implementation registers its logic under the names found in the export. Rename on either side, and the other side must be updated to match.

## Import-Loss Rules (Why Export Wins)

After importing external code, Studio loses:

- The function bodies of guard sources / action sources (only a `return true` placeholder remains)
- Custom configuration in Event property schemas

Therefore: **treat export as the source of truth and avoid re-importing.** If an import is unavoidable, manually restore those sources in Studio before exporting again, or they are gone.

## Sync Flow (Studio → Code)

1. User edits the diagram in Studio → re-export overwrites the export file
2. **Read before you touch anything**: the export can be regenerated at any time — always re-Read it before working; never rely on memory
3. Diff the structural delta: state nodes, event types, transition branches, guard/action names (branch-order differences do NOT count as delta — the implementation may derive from an array)
4. Align the implementation by name: added/renamed guards, actions, state nodes, event payload types
5. Run the project's tests + type check; commit only when all green

## Sync Flow (Code → Studio)

**Names** added in the implementation (guards / actions / states / events) must be synced back into the Studio diagram, or the next export won't match the implementation. Flow: ask the user to add same-named elements in Studio (placeholder logic is fine), then verify after re-export. Typical miss: the implementation gained a new action on a transition (e.g. `handleDragEnd`) that the export doesn't have.

## Consistency Checklist (when asked "are the two sides in sync?")

- Compare the state tree node by node (including parallel regions, child states, `initial`)
- Event type sets + payload fields (the implementation narrowing a type does NOT count as delta, e.g. `string` → `ToolId | null`)
- Guard/action name sets must match on both sides; a `return true` placeholder in Studio is normal — real logic only needs to exist in the implementation
- Recognize behaviorally-equivalent differences: explicit swallow branches vs. bubble-through fallback, branch order of mutually exclusive guards — these are NOT desync
- Behavior outside the machine (event adapter layer, gesture translation, throttling) is out of sync scope — don't misread adapter changes as "the design is behind"

## Common Failure Modes (from baseline testing)

| Failure | Consequence | Correct approach |
|---|---|---|
| Hand-editing the Studio export "to keep in sync" | Next export silently overwrites; changes evaporate | Have the user edit in Studio and re-export |
| Changing structure only in the implementation, never syncing back to Studio | Two-way drift; names don't match after export | Name changes must exist on BOTH sides |
| Editing the export or implementation from memory | User just changed Studio; you edit based on a stale version | Re-Read the export before touching anything |
| Putting guard business logic into Studio source | Lost on import, or overwritten by placeholders | Business logic lives only in the implementation; Studio keeps names and context-derived logic |

## Red Lines

- NEVER Write/Edit a Studio export file (unless the user explicitly says "this file will no longer be exported from Studio")
- NEVER skip re-Reading the export before editing the implementation
- A name change not synced both ways = a planted landmine
